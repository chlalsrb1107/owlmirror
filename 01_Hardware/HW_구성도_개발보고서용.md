**LiDAR는 루프랙 프레임 중앙 최상단**에 고정한다. 차체에 가리면 하단 빔이 소실되어 근거리
물체를 놓친다. 반경 **6 m 이내는 물리적 사각지대**이며, 이 구간은 거리 대신 소리(배기음 크기)와
예측으로 보완한다.

**ReSpeaker 위치**: 차량 루프 또는 대시보드 중앙(전방 180° 커버). 마이크 하단에 방진 고무 패드를
대어 엔진 진동을 차단하고, 데드캣으로 풍절음에 대응한다.

## 4. 전원 계통 (❌ 미확정 — 보고서 작성 전 결정 필요)

```
   차량 전원 ──▶ [인버터 또는 보조배터리] ──┬──▶ 노트북 (어댑터)

   ReSpeaker : 젯슨 USB 버스전원(5 V) — 별도 전원 불필요
```

## 5. 대역폭 설계 — 이 값들이 왜 이렇게 정해졌는가

보고서에서 "왜 이 구성인가"를 설명할 때 쓸 수 있는 근거다. 코드의 상수와 직접 연결된다.

### (1) 카메라 프레임레이트를 30 Hz로 제한한 이유

| 설정 | 대역 | 판정 |
|---|---|---|
| 무제한 (122 fps × 4대 × 2.46 MB) | 약 **1,200 MB/s** | ❌ USB 대역 초과 |
| **30 fps 캡** (`MAX_FRAMERATE_HZ = 30.0`) | 약 **295 MB/s** | ✅ 데모 표시에 충분 |
| 실측 (4대 동시) | 124 fps / **305 MB/s** | ✅ |

더 중요한 이유는 **카메라 3대가 LiDAR 이더넷(r8152)과 같은 5 Gbps 독 구간(~400 MB/s)을
공유**한다는 점이다(나머지 1대만 노트북 USB3 포트에 직결). 이 구간이 포화되면 LiDAR UDP
패킷이 유실되고 거리 매칭이 통째로 망가진다.

| 독 5 Gbps 구간 부하 (30 fps 기준) | 대역 |
|---|---|
| 카메라 3대 × 73.7 MB/s (2048×1200 BayerGB8) | 약 **221 MB/s** |
| LiDAR UDP (753.6 pps × 1206 B) | 약 **0.9 MB/s** |
| 합계 / 실사용 상한 | **약 222 MB/s / ~400 MB/s** |

→ 실측 결과 **유실 0.1%, 10 ms 이상 공백 0회**. 이 실측은 **지금의 배선(독 3대 + 직결 1대)
그대로** 수행한 것이므로 결론은 유효하다 — **현재 배선 그대로 촬영 가능**.
⚠️ 다만 여유가 절반 수준이므로, 프레임레이트 캡(30 fps)을 올리거나 카메라를 독으로 더 옮기면
LiDAR 유실이 먼저 발생한다. 캡은 낮춘 채로 유지할 것.

### (2) 노출 상한을 8 ms로 건 이유 — 주행 중 모션블러

| 노출 | 50 km/h(13.9 m/s)에서 한 프레임 흐림 | 판정 |
|---|---|---|
| **8 ms** (`MAX_EXPOSURE_US = 8000`) | 11 cm | ✅ 허용 |
| 20 ms | 28 cm | △ |
| 223 ms (상한 없을 때 실측값) | **3.1 m — 형체 불명** | ❌ |

### (3) LiDAR 지면 제거가 필요한 이유 — 물리적 계산

VLP-16의 수직 FOV는 ±15°다. 1.7 m 루프랙에 올리면 **최하단 빔이 약 6.3 m 앞 노면에 닿는다**
— 하필 사각지대 반경 6 m 바로 바깥이다. 그래서 지면 필터가 없으면 어느 방향을 조회하든
"6 m에 노면"이 최근접으로 잡혀, 30 m 앞 구급차 대신 매번 아스팔트까지의 거리를 보고하게 된다
(실측으로 확인된 현상). → 노면 기준 높이 0.3~1.5 m만 물체로 인정하도록 필터링.

## 6. 방향-카메라 배정 (✅ 2026-10-16 물리 검증 완료)

| 방향 | 캘리브레이션 ID | 시리얼번호 | 각도 |
|---|---|---|---|
| 전방 | cam2 | `FHH26070139` | θ = 0° |
| 좌측 | cam1 | `FHH26070138` | θ = +90° |
| 우측 | cam4 | `FHH26070137` | θ = -90° |
| 후방 | cam3 | `FHH26070140` | θ = 180° (기본 표시) |

**이 표는 실물로 검증된 값이다.** 2026-10-16에 각 방향에서 손을 흔들어 확인한 결과
**전방과 우측이 서로 바뀌어 있었고**, 위 표는 교정 후의 배정이다.

이전(2026-09-06 작성 시점)에는 `CAMERA_CALIB_ID`와 `daheng_ws_1/sync_cam.py`의 CAM1~CAM4
순서를 결합해 **유도한 값**을 적어뒀었다(전방=cam4/`FHH26070137`, 우측=cam2/`FHH26070139`).
그 유도가 실제 배선과 달랐다 — **배선 순서와 소프트웨어 순서가 어긋나도 코드는 절대
알아채지 못한다**는 경고가 그대로 현실이 된 사례다. 좌측 사이렌이 우측 화면에 떠도
아무 오류가 나지 않는다.

⚠️ 배정을 다시 바꿀 일이 생기면 **세 군데를 같이** 고쳐야 한다 — 내부 파라미터(fx, cx)는
방향이 아니라 **물리 카메라**를 따라가기 때문이다. 한쪽만 고치면 박스→방위 환산이 다른
렌즈의 fx를 써서 방위가 조용히 틀어진다.

| 고칠 곳 | 파일 |
|---|---|
| `CAMERA_SERIAL` | `08_Video_Demo/code/live_demo.py` |
| `CAMERA_INDEX_FALLBACK` | `08_Video_Demo/code/live_demo.py` |
| `CAMERA_CALIB_ID` | `08_Video_Demo/code/camera_bearing.py` |

### 검증 절차 (장착을 다시 하면 반드시 재실행)

```bash
~/owlmirror_venv/bin/python3 08_Video_Demo/code/preflight_view.py
```

카메라 4분할 + LiDAR BEV가 한 화면에 뜬다. **각 방향에서 손을 흔들어** 화면의
FRONT/LEFT/RIGHT/REAR 칸이 실제 방향과 맞는지 확인한다. 실내에서 화면이 어두우면
`--max-exposure 40`을 붙인다(주행 중에는 쓰지 말 것).

## 7. 센서 구성 근거 (멘토 발표 자료 · 보고서 인용용)

| | 오디오만 | 카메라만 | **카메라+LiDAR (채택)** |
|---|---|---|---|
| 방향 정확도 | ±20° | ±0.1° | **±0.1°** |
| 거리 정확도 | 측정 불가 | ±15~25% | **±2%** |
| 야간 동작 | 가능 | 제한적 | **가능** |
| 악천후 동작 | 가능 | 취약 | **가능** |
| 차량 특정 | 불가 | 조건부 | **가능** |

오디오는 360° 전방향을 항상 듣는 대신 방향이 거칠고, 카메라·LiDAR는 정밀한 대신 시야 안의
것만 본다. 세 센서를 겹쳐 **"소리로 먼저 알아채고, 카메라·LiDAR로 확정한다"**는 구조가 이
조합의 핵심이다.

## 10. 사전 점검 순서 (촬영·시연 당일)

```bash
# 1. 카메라 4대 + LiDAR 동시 확인 (GUI)
~/owlmirror_venv/bin/python3 08_Video_Demo/code/preflight_view.py
#    → 4분할 영상 + BEV 점군이 뜨는지, 각 방향에서 손 흔들어 배정 검증

# 2. 젯슨 링크 확인 (노트북에서 수신 모니터)
python3 08_Video_Demo/code/monitor_rx.py --seconds 30
#    → 주행 소음 바닥을 보고 --min-db 권장값 확인

# 3. 젯슨 실행 (젯슨에서)
python3 jetson_audio_sender.py --host 192.168.10.1
#    → 기동 시 "[*] PANNs 장치: cuda (Orin)" 출력 확인

# 4. 본 화면 실행 (노트북에서)
python3 08_Video_Demo/code/live_demo.py --fullscreen
```

⚠️ **종료는 반드시 Ctrl+C로.** 젯슨에서 SSH 창을 그냥 닫으면 파이썬이 살아남아 마이크를 계속
점유하고(`arecord -l`에서 `Subdevices: 0/1`), 다음 실행이 "마이크 못 찾음"으로 죽는다.
