# S/W 구성도 — 개발보고서 작성용 정리 (2026-09-05)

> 이 문서는 개발보고서 "S/W 구성도" 절을 쓰기 위해, 흩어져 있는 설계 문서와 **실제 동작 코드**를
> 대조해 정리한 것이다. 다른 컴퓨터로 인계할 때 이 파일 하나만 봐도 되도록 자립적으로 작성했다.
>
> ⚠️ **가장 중요한 전제**: `07_System_Integration/전체_시스템_통합.md`의 ROS2 구성은 **설계안**이고,
> 실제로 동작해서 2026-09-02 통합 테스트를 통과한 구현(`08_Video_Demo/code/`)에는 **ROS2가 들어가
> 있지 않다** (`rclpy` import 0건, 단일 프로세스 + 스레드 구조). 보고서에 실측 수치와 함께 쓸
> 구성도는 아래 "현행 구성"이며, ROS2는 "향후 확장" 절로만 남긴다.

## 0. ROS2 채택 여부 — 현행 유지로 결정 (2026-09-05)

**결론: 9/8 제출까지 ROS2는 도입하지 않는다.**

판단 근거

- ROS2가 제공하는 것은 (1) 프로세스·기기 간 pub-sub, (2) 메시지 직렬화, (3) rosbag 기록,
  (4) rviz 등 툴링이다. 그런데 현재 무거운 데이터(카메라 4채널 **305 MB/s**, LiDAR 점군)는
  **전부 노트북 한 프로세스 안에 머물러 프로세스 경계를 넘지 않는다.** 경계를 넘는 것은
  젯슨→노트북 JSON 한 줄(약 1 Hz)뿐이고, 그 링크는 UDP로 이미 **300+패킷 유실 0**으로 검증됐다.
- 도입 비용이 크다: 노드 분리 재작성 + 커스텀 msg 패키지 `colcon build` + 카메라 4대 대역에 대한
  DDS 튜닝(공유메모리/intra-process 설정을 하지 않으면 현행보다 느려진다). 촬영일까지 남은
  기간에 **검증되지 않은 코드로 촬영하게 되는 리스크**가 실익보다 크다.
- 현행 구현이 ROS2로 얻으려던 것을 이미 갖추고 있다: 배경 스레드 + "최신값 1건 보관" 패턴,
  링크 끊김 감지, 센서별 독립 실패(폴백) 처리.

ROS2가 값을 하는 시점 (향후 조건부 전환)

- 연구실(멘토 측)이 LiDAR 연결·동기화를 맡아 결과를 토픽으로 넘겨주는 구조가 될 때
- 처리를 여러 대 컴퓨터로 분산할 때
- rosbag으로 주행 데이터를 기록·재생해 오프라인 튜닝을 할 때

전환 난이도는 낮다 — 노트북에 ROS2 Humble이 이미 설치돼 있고(`/opt/ros/humble`),
`audio_receiver.py`가 수신부를 이미 분리해 둬서 `bridge_node` 하나만 얹으면 된다.

## 1. 젯슨 ↔ 노트북 통신 프로토콜

| 항목 | 값 |
|---|---|
| 전송 방식 | **UDP 단방향** (젯슨 → 노트북), JSON 한 줄 페이로드 |
| 포트 | **9870** (`DEFAULT_PORT`) |
| 물리 연결 | **이더넷 직결** (USB 랜 어댑터 사용, 주행 중 Wi-Fi 끊김 회피) |
| 고정 IP | 젯슨 **192.168.10.2** / 노트북 **192.168.10.1** |
| 전송 주기 | 실측 **약 1.0초** (0.98회/초). 인터페이스 스펙 목표는 250 ms(4 Hz) |
| 링크 실측 | 실입력 **300+패킷 유실 0** (2026-09-02) |
| 전송 내용 | 오디오 분류 결과 + 방향만. **영상·점군은 이 링크로 오가지 않는다** |

### 페이로드 스키마 (`08_Video_Demo/code/jetson_audio_sender.py`)

```json
{"seq": 1234, "t": 1751250042.318, "class": "siren", "conf": 0.91,
 "score": 1.83, "theta": 194.0, "sigma": 10.0, "rms_db": -22.4}
```

| 필드 | 설명 |
|---|---|
| `seq` | 0부터 증가. 수신측 유실 검출용 |
| `t` | 분석 구간의 **중심 시각**(구간 시작 시각 아님), 젯슨 시계 기준 |
| `class` | `car_horn` / `siren` / `motorcycle` / `none` (비경보 클래스는 `none`으로 눌러 보냄) |
| `conf` | 0~1 유사 신뢰도 — SVM이 `probability=False`라 보정된 확률이 아님. **표시용만** |
| `score` | SVM `decision_function` 원시 마진 — **임계값 판단은 이 값으로** |
| `theta` | **차량 좌표계** 방위각(전방 0°, 반시계 +). 마운트 오프셋 적용 완료 |
| `sigma` | 방향 오차 표준편차(도) — BEV 부채꼴 폭 = `2 × sigma` |
| `rms_db` | 분석 구간 ch0의 RMS 음량(dBFS). "가장 큰 경적 선택", "배기음 크면 사각지대 추정" 규칙에 사용 |

### 수신부 동작 (`audio_receiver.py`)

- 배경 스레드로 계속 수신하고 **최신 1건만 보관**(UDP 순서역전·밀린 패킷 대비, 2초 초과 패킷은 폐기)
- `seq` 공백으로 유실 수를 집계
- **5초간 패킷이 없으면 링크 끊김으로 판정** → 화면 좌하단 "젯슨 연결 끊김" 표시.
  (설계 원칙: 링크가 죽었을 때 마지막 감지가 화면에 영원히 남아 **화면이 거짓말하지 않게** 하는 것)

### 그 외 센서 링크

| 구간 | 방식 |
|---|---|
| ReSpeaker → 젯슨 | **USB**. 펌웨어 온보드 DoA를 USB Tuning 인터페이스 control transfer로 읽음(`pyusb`, `DOAANGLE` id=21) |
| VLP-16 → 노트북 | **이더넷 UDP:2368** (별도 USB 랜 어댑터, 192.168.1.100). 실측 753.6 pps, 유실 0.1% |
| 카메라 4대 → 노트북 | **USB3 Vision** (Daheng MER2-240-159U3C, `gxipy` SDK). 실측 124 fps / 305 MB/s |

⚠️ 시계 동기화: `t`가 젯슨 시계 기준이므로 두 기기에 chrony/NTP가 필요하다. 수신부는 스큐가 1초를
넘으면 경고만 출력하고 보정하지는 않는다.

⚠️ 함정: 젯슨과 노트북 IP가 겹치면 통신이 **전혀** 안 되는데 핑은 성공하는 것처럼 보인다(루프백이
응답). 반드시 젯슨 `.2` / 노트북 `.1`로 고정할 것.

## 3. 거리 측정 방식

**LiDAR 직접 측정 + 소리 방향 매칭.** 이전 설계(depth 카메라, YOLO bbox 기반 단안거리 추정,
음량 변화 기반 추정)는 **전부 폐기**되었다. 소리로 거리를 계산하지 않는다 — 거리는 VLP-16이
직접 재고(정확도 ±2%), 오디오·카메라는 "그 거리에 있는 어느 물체가 소리를 냈는지"를 지목하는
매칭 역할만 한다.

### 처리 순서 (`08_Video_Demo/code/lidar_distance_match.py`)

1. VLP-16 UDP(2368) 패킷을 배경 스레드로 디코드(`velodyne-decoder`, VLP-16 공장 캘리브레이션 내장)
   → 최신 스캔을 차량 좌표계 `(x, y, z, range_m, azimuth_deg)` 배열로 보관
2. 오디오 방향 `theta` **± 25°**(`DEFAULT_ANGLE_MARGIN_DEG`) 각도 창 안의 포인트만 추출
3. **지면 제거** — 노면 기준 높이 **0.3 m ~ 1.5 m**만 물체로 인정
   (VLP-16 수직 FOV ±15°, 1.7 m 루프랙 장착 시 최하단 빔이 약 6.3 m 앞 노면에 닿는다. 필터가
   없으면 어느 방향을 조회하든 "6 m에 노면"이 최근접으로 잡혀 30 m 앞 구급차 대신 매번
   아스팔트 거리를 보고한다 — 실측으로 확인된 현상)
4. **거리축 클러스터링** — 정렬된 거리에서 간격 **1.0 m** 이상이면 다른 물체로 분리,
   **5점 이상** 덩어리만 물체로 인정하고 그 **중앙값**을 거리로 반환
   (최근접 점 하나만 보면 노이즈 한 점에 거리가 끌려간다)
5. 반경 **6 m 이내는 물리적 사각지대**로 거리를 신뢰하지 않는다 → 거리 숫자 대신
   BEV에서 "사각 구역 점등"으로 표시
6. 확정된 거리를 경보 등급 판정에 사용 (오토바이: 사각지대/15 m 이내 = 경고, 15~25 m = 주의)

### 폴백

LiDAR가 죽거나 `LIDAR_AVAILABLE=False`여도 앱 전체는 죽지 않는다. **거리 숫자와 점 클러스터만
빠지고** 링·자차·방향 부채꼴은 오디오만으로 계속 그려지며, 좌하단에 "LiDAR 미연결 — 방향만 표시"가
명시된다. (사이렌은 거리와 무관하게 항상 경고, 오토바이는 카메라 Detection·배기음 경로가 따로
있으므로 "라이다 없으면 전부 주의로 캡"하던 예전 폴백은 더 이상 쓰지 않는다.)

### ⚠️ 미검증 항목 (보고서에 단정적으로 쓰면 안 되는 것)

- 라이다 좌표계 → 차량 좌표계 **요(yaw) 오프셋** 실측 (`MOUNT_OFFSET_DEG`, 마이크용과 별개 값)
- 마운트 높이 `MOUNT_HEIGHT_M = 1.7` — 장착 후 줄자 실측값으로 교체 필요
- `MIN_CLUSTER_POINTS = 5` — 멀수록 점이 줄어 놓칠 수 있어 실차 시험 후 조정 필요
- 각도 창 ±25° — 펌웨어 DoA 오차 범위 추정치

## 4. HMI 구현 방식 — **웹 아님. 파이썬 네이티브(OpenCV) 앱**

HTML 파일(`06_Display_Integration/bev_mockup.html`, `08_Video_Demo/camera_ui_mockup.html`)은
**디자인 목업 전용**이다. 실제 화면은 다음과 같이 구현돼 있다.

| 항목 | 내용 |
|---|---|
| 프레임워크 | **OpenCV `imshow` 전체화면 단일 창** (`live_demo.py` + `bev_render.py`) |
| 해상도 | 캔버스 1600×900(16:9)으로 그리고, `xrandr`로 외장 디스플레이 해상도를 읽어 **1920×1080에 여백 없이 자동 대응** |
| 레이아웃 | 좌우 반반 — **왼쪽 BEV 원형 지도**, **오른쪽 카메라 영상**, 상단 알림 배너 |
| BEV 표현 | 단순 마커가 아니라 **LiDAR 실제 리턴 포인트**를 그린다. 지면 제거 통과분=흐린 회색 점, 매칭 확정=클래스 색 재채색+후광+거리 라벨, 미확정=부채꼴(폭 `2×sigma`), 6 m 이내=사각 구역 점등 |
| 카메라 전환 | 기본 후방, 소리 방향에 맞는 카메라로 자동 전환(4대 모두 미리 열어 두어 전환 지연 없음) |
| 한글 출력 | `cv2.putText`가 한글을 못 그려 **Pillow로 텍스트 레이어 합성**. 내용이 바뀔 때만 재생성하는 캐시 적용(캐시 없으면 텍스트 합성만으로 14 ms 소요) |
| 성능 | **6~8 ms/프레임** (감지 2건 6.7 ms, 평상시 4.8 ms) — 카메라 상한 30 Hz에 여유 |
| 스레드 구조 | 수신·YOLO·LiDAR 매칭 = 백그라운드 스레드, 렌더링·창 = 메인 스레드(OpenCV 제약). 둘 사이는 락으로 보호되는 `SharedState`로만 통신 |

**프레임워크 결정 이력**: `06_Display_Integration/영상_파이프라인.md`에는 "웹(rosbridge+roslibjs) vs
네이티브(PyQt) 미정"으로 적혀 있으나, 2026-09-02 구현으로 **OpenCV 네이티브로 결론**났다.
그 문서는 갱신되지 않은 상태다.

### 화면 설계 전제 (보고서에 함께 쓰면 좋은 내용)

**주 사용자는 청각장애인 운전자다.** 따라서 (1) 소리로 보완할 수 있다고 가정하지 않고 화면이 유일한
전달 경로이며, (2) 정보마다 그림과 글자를 함께 주고(소리 종류=아이콘+이름, 방향=회전 화살표+"좌측"),
(3) 경고 단계에서는 거리에 반비례하는 주기(0.3~1.2초)로 테두리를 깜빡여 **주변시야에 걸리게** 한다.
상세: `06_Display_Integration/ui_state_spec.md` §1-1.

동시 감지 처리 원칙은 **"지도는 전부, 알림은 하나"** — BEV에는 감지된 모든 대상을 좌표로 표시하고,
상단 배너와 테두리 빛은 최우선 대상 하나만 반영한다.

│         │                                                          │
│         └─▶ alert_policy.py ─ 표시 / 주의 / 경고 판정              │

## 6. 향후 확장 — ROS2 전환안 (보고서의 "확장성" 절용)

전환 시 구조는 다음과 같다. 현행 코드에서 바뀌는 것은 **모듈 경계에 토픽을 끼우는 것**뿐이고,
각 모듈의 알고리즘은 그대로 재사용된다.

| 토픽 | 발행 조건 | 내용 |
|---|---|---|
| `/audio/detection` | 상시 | 젯슨 분류·DoA 결과 (`bridge_node`가 UDP→토픽 republish) |
| `/camera_{front,rear,left,right}/image_raw` | 상시 | 카메라 4대 영상 |
| `/velodyne_points` | 상시 | LiDAR 포인트클라우드 (`velodyne_driver`/`velodyne_pointcloud`) |
| `/vehicle/candidates` | 오디오 트리거 시에만 계산 | LiDAR+카메라+오디오 매칭 결과 |
| `/ui/state` | `/vehicle/candidates` 갱신 시 | 화면 상태 (IDLE/표시/주의/경고) |

원칙: 카메라·LiDAR 노드는 부팅 시 한 번 실행 후 **상시 퍼블리시**한다. 오디오 감지는 노드 실행/종료가
아니라 다운스트림(YOLO 검출, 거리 매칭)의 **처리 시작 조건**으로만 작동한다 — LiDAR는 기계식이라
스핀업 지연이 크고, 카메라 캡처 자체는 가벼워 상시 유지가 유리하다.

메시지 타입은 프로토타입 단계에서 `std_msgs/String`(JSON)으로 시작하고, 정식 구현에서는 커스텀
`AudioDetection.msg`(t / class_name / conf / score / theta / sigma / rms_db) 패키지로 교체한다.

## 7. 보고서 작성 시 주의 — 아직 미검증인 것

단정적으로 쓰면 안 되는 항목들이다.

| 항목 | 상태 |
|---|---|
| `MOUNT_OFFSET_DEG` (마이크·라이다 각각) | **미실측**. 차량 정면 0° 보정이 안 돼 있음 |
| 방향 **정확도** | σ 5~7°는 **정밀도(흩어짐)**이지 정확도가 아님. 실제 방향과 일치하는지는 미검증 |
| 차량 실장착 | 미완 — 카메라 방향 배정은 유도값 |
| 음량 임계값 (`MOTO_LOUD_DB` 등) | 전부 실내·정지 기준. `rms_db`는 dB SPL이 아닌 상대값이라 주행 소음에서 재조정 필수 |
| 오토바이 검출률 | **13%** (모델 한계) — 사이렌 83%와 함께 정직하게 기재할 것 |
| 오경보 차단 | score/margin 사용 불가로 음량으로 우회 중 |
| LiDAR 실물 연동 | 렌더링만 검증됨. 실제 포인트가 BEV에 제대로 뜨는지, 각도 규약이 차량 기준으로 맞는지 미확인 |
| 방풍 커버(데드캣) | 확보 완료·정지 상태 확인. **주행풍(30~50 km/h)에서는 미검증** |

### 각도 규약 주의

시스템 `theta`는 **전방 0°, 반시계 +**(`select_camera(90) == "left"`)인데, 목업 SVG는 시계 +
(0=전, 90=우)로 그려져 있다. `bev_render._screen_angle()`에서 **한 번만** 부호를 뒤집어 맞춘다 —
빠뜨리면 BEV 전체가 좌우 반전돼 왼쪽 사이렌이 오른쪽에 뜬다. 구성도나 도식을 그릴 때도 주의.
