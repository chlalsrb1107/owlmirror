## 시스템 아키텍처 — Jetson/노트북 분리 (신규 확정)

기존에는 Jetson 한 대가 오디오+영상+거리+화면을 전부 처리하는 구조로 설계돼 있었으나, **Jetson은 오디오만 전담**하고 나머지는 노트북이 처리하는 구조로 전환됨.

```
[Jetson] 오디오 전담
  - 4채널 수음 (마이크 어레이 입력)
  - 소리 종류 분류 (사이렌·경적·배기음)
  - 소리 방향 추정 (오차 ±10~20°)
  → 초당 4회, 아래 JSON 한 줄만 노트북으로 전송 (영상·점군은 오가지 않음)

[노트북] 영상·거리·화면
  - 소리 방향에 해당하는 카메라 영상 확인
  - 경광등 점멸 검출 (평상시 경로, 학습 없이 ~0.5초)
  - 야간/악천후로 경광등이 안 보이면 소리 방향 변화 + 차량 움직임 대조 (대체 경로)
  - LiDAR로 후보 차량들의 거리 측정 → 소리 방향과 맞는 차량 특정
  - BEV 지도 + 테두리 알림으로 화면 표시
```

### Jetson→노트북 인터페이스 (JSON, 초당 4회)

```json
{
  "t": 1751250042.318,
  "class": "siren",
  "conf": 0.91,
  "theta": 194.0,
  "sigma": 12.0
}
```

| 필드 | 설명 |
|---|---|
| `t` | 분석 구간의 **중심 시각** (구간 시작 시각 아님) |
| `class` | `siren` / `horn` / `motorcycle` / `none` |
| `conf` | 0.0~1.0 |
| `theta` | 차량 좌표계 방위각 (전방 0°, 반시계 +) |
| `sigma` | 방향 오차 표준편차(도) — BEV 부채꼴 폭(`2×sigma`)에 사용 |

**시각 동기화 원칙**: LiDAR는 한 바퀴 스캔에 100ms가 걸려 같은 프레임 안에서도 관측 방향에 따라 최대 100ms 시각차가 생김(50km/h면 100ms에 약 1.4m 이동) → **프레임 시각이 아니라 점(대상)별 시각을 사용**해 오디오와 매칭. 자세한 내용은 `06_Display_Integration/ui_state_spec.md` §7 참고.

### 통신 미들웨어 및 물리 연결 (2026-08-17 논의, 세부 구현 확정 필요)

**확정된 것**
- **노트북**: ROS2 사용 (기기: ASUS TUF A16, 우분투 기반)
- **젯슨**: ROS 미설치 — 경량 소켓(UDP 또는 ZeroMQ PUB/SUB)으로 위 JSON만 전송, ROS 의존성 없이 유지
- **물리 연결**: 이더넷 케이블 직결 권장 (주행 중 Wi-Fi 연결 끊김 회피). 일반 랜케이블로 가능(요즘 NIC는 auto-MDIX 지원, 크로스오버 케이블 불필요), 양쪽 고정 IP 수동 설정 필요(1:1 직결이라 DHCP 없음)
- **카메라(4대)·LiDAR(VLP-16) 노드는 부팅 시 한 번 실행 후 상시 퍼블리시** — 오디오 감지로 트리거되는 것은 노드 실행/종료가 아니라 다운스트림(YOLO 검출, 거리 매칭) 노드의 "처리 시작 조건"뿐. LiDAR는 기계식이라 켰다 껐다 하면 스핀업 지연이 커서 상시 구동 필요

**노트북 쪽 필요 구성 요소**
- **브릿지 노드**(`rclpy`): 젯슨 소켓 JSON을 수신해 `/audio/detection` ROS2 토픽으로 republish
  - 메시지 타입: 프로토타입은 `std_msgs/String`(JSON 문자열), 정식 구현은 커스텀 msg(`AudioDetection.msg`: t/class_name/conf/theta/sigma) 패키지 작성 후 `colcon build`
- LiDAR: 공식 `velodyne_driver`/`velodyne_pointcloud` 패키지로 `/velodyne_points` 상시 퍼블리시
- 카메라: `usb_cam` 또는 `v4l2_camera` 노드 4개 → `/camera_{front,rear,left,right}/image_raw`
- 토픽 구조(안): `/camera/{dir}/image_raw`, `/velodyne_points`, `/audio/detection`(상시) → `/vehicle/candidates`(오디오 트리거 시에만 계산) → `/ui/state`

**젯슨 쪽 필요 구성 요소**
- `realtime_classify.py`에 소켓(UDP 또는 zmq) 송신 로직 추가 필요 (현재는 콘솔 출력만 함)
- 고정 IP + 노트북과 시계 동기화(chrony/NTP 등) — 위 "점별 시각 매칭" 정확도가 두 기기 시계 일치 여부에 좌우됨

**(2026-08-17 갱신) 주기 불일치 — 구조적으로 해결, 근본 원인(추론 속도)은 미해결**
- 실외 실측에서 분류 1회 추론이 15초를 넘는 경우까지 관측됨 → `realtime_classify.py`를 방향추정(메인 스레드, GCC-PHAT, 0.25s 주기)과 분류(백워커 스레드, PANNs+SVM)로 분리하는 구조로 재작성함
  - 방향(theta)은 분류 속도와 무관하게 항상 인터페이스 스펙대로 초당 4회 갱신 가능
  - 분류 결과는 큐 크기 1(가장 최근 윈도우만 유지, 밀리면 이전 것 폐기) + `--stale-sec`(기본 2.5s) 초과 시 폐기 — 오래된 분류로 잘못된 위치에 마커 찍는 것 방지
  - `--device auto|cpu|cuda` 옵션 추가해 CUDA 사용 여부 확인 가능하게 함 (단, Jetson에 CUDA 지원 torch가 실제로 설치돼 있는지는 별도 확인 필요 — 아래 참고)
- **여전히 미해결**: 왜 추론이 2s~15s로 널뛰는지의 근본 원인. 유력 용의자는 "Jetson 내장 GPU 미인식, CPU로만 동작"(아래 실시간 추론 파이프라인 섹션 참고) — `torch.cuda.is_available()` 확인 및 Jetson용 CUDA 지원 PyTorch(JetPack/L4T 빌드) 설치 확인이 최우선. 그다음 TensorRT 변환(FP16) 검토
- `--stale-sec` 기본값(2.5s)은 50km/h 기준 약 35m 이동 거리로 잡은 값 — 실측 지연 분포 보고 조정 필요. 만약 15s 지연이 흔하면 대부분의 분류 결과가 폐기되어 시스템이 "표시(방향만)" 단계에 계속 머무는 것으로 저하됨 — 이는 안전한 열화(fail-safe)이지 진짜 해결책은 아니므로 GPU/TensorRT 작업이 우선순위

**(2026-08-17 추가) GPU 미인식 문제 원인 확인 및 해결됨**
- 원인: `pip install torch`로 설치된 게 일반 PyPI 빌드(`torch 2.12.1+cu130`)였음 — 이 젯슨(JetPack 6.x, L4T R36.4.7, CUDA 12.6)의 Tegra 내장 GPU용으로 빌드된 게 아니라 x86/dGPU용 CUDA 13.0 스택을 기대하는 빌드라 `torch.cuda.is_available()`이 계속 False였음
- 해결: NVIDIA Jetson AI Lab이 JetPack별로 따로 빌드해 배포하는 pip 인덱스(`https://pypi.jetson-ai-lab.io/jp6/cu126`)에서 설치. **주의**: `--extra-index-url`로 일반 PyPI를 같이 열어두면 pip이 버전 높은 일반 빌드를 다시 골라버려 문제가 재발함 — 반드시 `--index-url`만 쓰고 버전을 명시할 것
  - 처음 시도한 `torch==2.11.0`은 `libcudss.so.0` 공유 라이브러리 누락으로 import 자체가 실패함(이 인덱스엔 대응하는 cuDSS 패키지가 없음, aarch64용 `nvidia-cudss-cu12`도 PyPI에 없음) → 한 버전 낮은 `torch==2.8.0` + `torchvision==0.23.0` 조합으로 정상 동작 확인
  - 확인됨: `torch.cuda.get_device_name(0)` → `"Orin"`, capability `(8, 7)`
- **실측 벤치마크** (실제 체크포인트, 유휴 상태 기준, 1.0s 오디오 윈도우): CPU 평균 278ms → CUDA 평균 78ms (약 3.6배)
  - ⚠️ 이 78ms는 카메라·LiDAR·ROS2 없이 이 스크립트 하나만 유휴 상태에서 돌린 수치라, 기존에 관측된 "실외 15초" 현상을 이 벤치마크만으로 완전히 설명한다고 단정할 수 없음 — 다른 노드들과 동시 구동 시, 그리고 실제 실외(발열/직사광선에 의한 Orin Nano 스로틀링 가능성)에서 재측정 필요
  - `pip3 check` 결과 `torchvision`/`ultralytics` 등 다른 패키지와 충돌 없음 확인 (orphan 패키지 경고 2건은 무관)
- 다음 단계: 위 벤치마크만으로도 실시간 목표(초당 4회, 250ms)에 여유 있게 들어오므로, TensorRT 변환은 급하지 않을 수 있음 — 우선 젯슨에서 카메라·LiDAR·ROS2까지 다 켠 상태로 `realtime_classify.py --device cuda` 재측정해서 실사용 환경 지연부터 확인할 것

## 거리 추정 방식 전환 (중요 — 기존 설계 폐기)

- **기존**: RGB 단안거리 추정 (YOLO bbox 폭 기반) 또는 회의에서 논의됐던 "볼륨 변화 패턴 기반 거리 추정"

- 볼륨 기반 거리 추정 아이디어(7/5 회의)는 최종적으로 **채택되지 않음**

  - **의도적인 클래스 구성으로 확인됨** — 기존에 언급됐던 타겟 4클래스(`car_horn / emergency_siren / motorcycle_exhaust / background`) 표기와 이름이 다르지만, 단일 `background` 클래스 대신 실제 도로 환경에서 흔한 비타겟 소음(`children_playing`, `engine_idling`)을 명시적으로 학습시켜 배경음 역할을 하도록 한 설계 — 위 "실시간 추론 파이프라인"의 기존 한계("학습 클래스에 background 없음")를 이 방식으로 해결한 것
  - `siren`, `motorcycle`은 각각 `emergency_siren`, `motorcycle_exhaust`에 대응 (문서상 표기만 축약형)
  - 판단 로직 상으로는 `car_horn`/`siren`/`motorcycle` 3개는 경보 대상, `children_playing`/`engine_idling`은 비경보(배경) 클래스로 매핑하면 됨
  - **아키텍처는 AST가 아니라 PANNs Cnn14(16kHz) 임베딩 + SVM 분류기** — 체크포인트(`best.pt`)를 직접 열어 확인함. `realtime_classify.py`를 이 조합으로 재작성해 실제 로드·추론 확인 완료(더미 오디오 기준)
  - ⚠️ 재현 불완전한 부분: (1) 체크포인트의 `semantic_thresholds`를 적용하는 정확한 방식(AudioSet 클래스 인덱스 매핑)을 알려줄 학습 스크립트가 없어 미적용, (2) SVC가 `probability=False`로 학습돼 확률 대신 `decision_function` 마진 점수만 출력, (3) `embeddings.pt`/`embeddings_v3.pt`(멀티뷰)로 볼 때 학습이 멀티뷰 평균을 썼을 가능성 있으나 실시간 추론은 단일 임베딩만 사용 — 상세는 `03_Audio_Classification/model_outputs/panns_svm/README.md`
  - 이 저장소에는 가중치(`.pt`/PANNs 사전학습 `.pth`)가 없음(용량 문제로 git 제외 대상, `panns_svm/README.md`에 복원 방법 정리). PANNs Cnn14 사전학습 가중치는 `realtime_classify.py` 최초 실행 시 Zenodo에서 자동 다운로드됨(~340MB, 인터넷 필요) — SVM 체크포인트(`best.pt`)는 팀원과 별도 공유 방법 필요
- AI Hub 데이터·오토바이 배기음 직접 녹음 계획(`02_Data_Collection/데이터셋_수집_계획.md`)은 이 5클래스 모델을 보강하는 데이터로 이어지는 것으로 정리 — 기존 4클래스 표기는 이 5클래스 구성으로 갱신 필요

## 화면(UI) 설계 (BEV|카메라 반반 구성, 2026-09-01 갱신)

기존에 언급됐던 "카메라 영상 + HUD 오버레이"(`06_Display_Integration/영상_파이프라인.md`) 중심 설계에서, **위에서 내려다본 BEV(Bird's-Eye View) 지도**를 쓰는 방식으로 전환된 뒤, **(2026-09-01) 화면을 세로로 반 나눠 왼쪽 BEV·오른쪽 카메라를 상시 함께 띄우는 구성**으로 재정리됨. 카메라를 조건부 보조 화면(PIP)으로 격하했던 이전 안은 폐기 — 소리 없을 때도 카메라(기본 후방)는 항상 보이고, 감지 시 해당 방향으로 전환된다.

- 상세 사양: `06_Display_Integration/ui_state_spec.md`
- 인터랙티브 목업(최신, BEV|카메라 반반): `08_Video_Demo/camera_ui_mockup.html`
- 인터랙티브 목업(구버전, BEV 화면 전체): `06_Display_Integration/bev_mockup.html` — 개별 시각 요소 디자인 참고용으로만 남김
- ⚠️ 위 갱신은 목업·설계 문서 범위 — `08_Video_Demo/code/live_demo.py`는 아직 이 레이아웃으로 재구현되지 않음

### 화면 상태 4단계

| 상태 | 의미 | 상단 알림 | 지도 | 테두리 빛 |
|---|---|---|---|---|
| `IDLE` | 소리 없음 | 없음 | 표시 안 함 | 없음 |
| `표시` | 주변에 있으나 위험 아님 | 회색 한 줄 | 회색 점 | 없음 |
| `주의` | 접근 중/위치 미확정 | 노란 막대 | 부채꼴 또는 노란 마커 | 약하게(45%) |
| `경고` | 근접/사각지대/차량 확정 | 빨간 막대 | 빨간 마커 또는 구역 점등 | 강하게(90%) |

- **원칙**: 지도는 감지된 모든 대상을 표시, 상단 알림·테두리 빛은 최우선 대상 하나만 반영
- **위치 미확정 시에는 특정 차량에 마커를 찍지 않고 부채꼴(방향+오차범위)로만 표시** — "잘못된 지목은 알려주지 않는 것보다 위험하다"는 원칙
- 상태 진입은 즉시, 하향/해제는 지연(3초 유지 후 0.5초에 걸쳐 해제) — 소리가 순간 끊겨도 알림이 깜빡이지 않도록

### 소리 우선순위 (동시 감지 시, 2026-08-26 정정 — 사이렌·경적 순서 변경)

1. 오토바이·사각지대 진입 (충돌 최임박)
2. 오토바이·15m 이내 근접
3. 사이렌·차량 확정 (응급차량 양보 의무·법적 우선순위)
4. 사이렌·위치 미확정
5. 경적 (나를 향한 신호일 가능성은 있으나 양보 의무 있는 사이렌보다 후순위)
6. 오토바이·15~25m 접근
7. 오토바이·멀어짐 (알림 없음)

> 기존엔 경적을 "나에게 닥친 충돌 위험" 기준으로 사이렌보다 위에 뒀으나, "응급차량 양보 의무" 기준으로
> 재논의해 사이렌을 항상 경적보다 위로 정정함(오토바이 근접/사각지대는 물리적 충돌 기준이라 변경 없음).
> 상세 근거는 `06_Display_Integration/ui_state_spec.md` §2 참고. **(2026-08-31 갱신)** 9/8 데모
> (`08_Video_Demo/code/live_demo.py`)에 LiDAR 거리 매칭이 다시 들어오면서, 클래스만 보던 고정
> `PRIORITY` 딕셔너리 대신 `priority_rank(class_name, level, blind)` 함수로 바뀌어 이 7단계 표를
> (경적 제외) 그대로 반영함 — 사이렌은 차량 확정(경고)이냐 위치 미확정(주의)이냐로, 오토바이는
> 사각지대/근접(경고)이냐 15~25m 접근(주의)이냐로 순위가 갈린다. 동시 감지 시 우선순위 낮은 대상은
> 버리지 않고 화면 우측 상단에 작은 아이콘+방향으로 함께 표시(메인 카메라/배너는 1위만) — 이 부분은
> 8/26 결정 그대로 유지.

## 소리별 대응 방식 (오토바이 경고가 핵심 차별점)

| 소리 | 대응 |
|---|---|
| 사이렌(긴급차량) | 경광등 점멸로 찾음 → LiDAR로 거리 측정 → 지도에 차량 위치 표시 |
| 배기음(오토바이) | 골목·근접 주행 모두 대응, 벽 뒤는 소리로 미리 감지, 가까이 붙으면 지도 표시, 위험도 단계 구분 |
| 경적(일반 차량) | 즉각 방향 표시 + 해당 방향 카메라, **거리는 추정하지 않음** |

### 오토바이 경고 5단계

| 상황 | 단계 | 화면 표시 |
|---|---|---|
| 주변에 있으나 멀어짐 | 표시 | 회색 점, 알림 없음 |
| 15~25m 접근 | 주의 | 노란 마커 |
| 15m 이내 근접 | 경고 | 빨간 마커 + 테두리 빛 (깜빡임 주기 = 거리에 반비례, 0.3~1.2초) |
| 사각지대(반경 6m 이내, LiDAR 사각) 진입 | 경고 | 점 대신 **사각 구역 자체를 점등** (0.3초 고정 깜빡임) — 없는 정확도를 있는 것처럼 보이지 않기 위함 |
| 벽에 가린 골목 | 주의 | 부채꼴 + "시야 밖" 표시, 방향은 오토바이가 아니라 **골목 입구**를 가리킴 |

> 도심에서 매번 경고하면 운전자가 곧 알림을 무시하게 됨 → 상황별 단계 구분이 핵심. 기존 양산 차량 경고 기능(옆 차선 일부만 감지)과 달리 **360° 전방향 + 벽 뒤 골목 감지**가 차별점.

## 진행 계획 (M1~M5, 중간보고 기준)

| 단계 | 내용 | 상태 |
|---|---|---|
| M1 | 소리 인식 개선 — 방풍 커버 장착 후 주행 정확도 재측정 | 준비 |
| M2 | 방향 추정 — 사이렌 전용 방향 추정 적용 | 준비 |
| M3 | 카메라 전환 — 소리 방향 카메라 화면 자동 표시 | **시연 가능** |
| M4 | 경광등 검출 — 점멸 인식 + LiDAR 거리 연결 | 확장 |
| M5 | 오토바이 경고 — 배기음 데이터 수집, 골목·근접 경고 | 확장 |

- **3단계(M3) 이후로는 언제든 시연 가능한 상태 유지**가 목표
- 측정 항목: 인식 정확도(속도별·소리 종류별), 방향 오차(실제 각도 대비), 지목 정확도(정답 차량 선택률), 오경보 횟수(일반 주행 10분당)
- 시험 방법: 다른 차량 지붕에 스피커를 얹고 함께 주행 → 그 차량이 정답. 긴급차량은 별도 학습 데이터 불필요, **오토바이 배기음만 직접 녹음** 필요 (주행 소음 섞어 학습해야 실도로 성능 유지)
