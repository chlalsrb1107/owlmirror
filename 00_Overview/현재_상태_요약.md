## ✅ 2026-09-02 — 실장비 첫 통합 테스트 (마이크 실입력 최초)

**젯슨(ReSpeaker) + 카메라 4대 + LiDAR + 화면이 처음으로 한 번에 돌았다.** 그동안 오디오는
더미/simulate로만 검증했는데, 이날 처음으로 실제 마이크 입력을 태웠다.

### 실측으로 확정된 것 (문서의 "미검증" 항목 해소)

| 항목 | 이전 기록 | 2026-09-02 실측 |
|---|---|---|
| `DOAANGLE` 레지스터 id=21 | "공식 참고값, 실측 안 됨" | ✅ **정상 동작 확인** |
| 방향 정밀도 | ±10~20° 추정 | **σ ≈ 5~7°** (정지·실내, 사이렌 고정) |
| 젯슨 PANNs 추론 속도 | "CPU면 1회에 수 초" 우려 | **1.0초 창에 약 0.2초** — 우려는 기우였다 |
| 젯슨→노트북 UDP 링크 | simulate 입력으로만 검증 | ✅ **실입력 300+패킷 유실 0** |
| 카메라 4대 + LiDAR 동시 | 미검증 | ✅ **124 fps(305 MB/s) / LiDAR 753.6 pps 유실 0.1%** |
| 전체 파이프라인 통합 | 미검증 | ✅ **동작. BEV에 실제 점군, 실제 카메라, 실제 감지 표시** |

- 독 5Gbps 허브에 카메라 2대+LiDAR 이더넷이 몰려 있어 대역 경합을 우려했으나 **실측상 문제없음**
  (유실 0.1%, 10ms+ 공백 0회). 지금 배선 그대로 촬영 가능

### 분석 구간 길이 확정 — `--seconds 1.0 --interval 0`

| | `--seconds 0.5` | `--seconds 1.0` (확정) |
|---|---|---|
| 주기 | 0.55s | **1.22s** |
| 사이렌 검출률 | 35% | **83%** |
| 초당 감지 횟수 | 0.64회 | 0.68회 |

초당 감지 횟수는 사실상 같은데 검출률이 2.4배 차이난다 — 사이렌은 주파수가 오르내리는 소리라
한 주기가 1~2초인데 0.5초 창에는 특징이 반밖에 안 담긴다. 검출률이 낮으면 배너가 깜빡인다.
**기본값을 `--interval 0`(기존 2.0)으로 바꿔 주기를 3.19초 → 1.22초로 당겼다** — 느린 원인은
추론이 아니라 sleep이었다.

### 새로 드러난 문제

1. **`score`/`margin`을 신뢰도로 쓸 수 없다.** sklearn SVC 다중클래스 OvR 값은 "이긴 1:1 대결
   수(0~4) + 소수점(<1/3)" 구조라, 확신 있는 예측이면 클래스와 무관하게 늘 4.2가 나온다
   (siren +4.27 / none +4.23 / motorcycle +4.23, 범위 완전 중첩). 1위–2위 격차(`margin`)를
   추가로 보내도록 했으나 그것도 겹친다(siren 0.68 / none 0.60). **임계값으로 오경보를 거르는
   방법이 현재 없다** — SVC를 `probability=True`로 재학습해야 한다
2. **DoA 읽는 시점이 틀려 있었다.** 분류 뒤에 읽어서 캡처 시작 +3.2초 시점이었고, 소리가 끊긴
   뒤라 theta가 랜덤(σ 61°)이었다. **수음 직후로 옮겨 σ 7°로 개선**
3. **Detection 오검출** — 사이렌 감지 중 실험실 책상이 "Motorcycle 48%"로 잡혀 화면 전체에
   박스가 그려졌다. 신뢰도 임계값(0.55)과 소리↔라벨 대조(`DETECTION_EXPECT`)를 추가해 차단
4. **조용할 때 theta가 흔들린다** — 사이렌이 끊긴 구간에서 222°, 79° 같은 값이 섞인다.
   `rms_db`가 낮으면 방향을 신뢰하지 않는 처리가 필요할 수 있음 (미구현, 확인 필요)
5. **운영 함정**: SSH 창을 그냥 닫으면 젯슨 쪽 파이썬이 살아남아 마이크를 계속 점유한다
   (`arecord -l`에서 `Subdevices: 0/1`). 다음 실행이 "마이크 못 찾음"으로 죽는데 원인이
   안 보여 두 번 헤맸다 → 오류 메시지가 이 경우를 구분해 알려주도록 수정. **종료는 Ctrl+C로**

### 네트워크 주의

젯슨과 노트북이 **둘 다 192.168.10.2**로 설정돼 있어 통신이 전혀 안 됐다. 핑이 성공하는 것처럼
보이지만 자기 자신(루프백)이 답한 것이고, 젯슨에서 `--host 192.168.10.2`로 쏘면 패킷이 젯슨
안에서 돈다. **노트북을 192.168.10.1로 변경**해 해결. 젯슨 = `.2`, 노트북 = `.1`,
젯슨 실행 시 `--host 192.168.10.1`.

## ⚠️ 2026-09-02 갱신 — BEV|카메라 반반 화면을 실제 코드로 구현

9/1까지는 "목업만 반반으로 바꾸고 실제 구현은 9/3 go/no-go 이후에 정한다"고 미뤄둔 상태였으나,
**최종 결과물에 BEV가 반드시 들어가야 한다는 판단으로 구현을 앞당겼다.** `live_demo.py`의 화면이
이제 목업과 같다 — 왼쪽 BEV 원형 지도, 오른쪽 카메라 영상.

- **신규 `08_Video_Demo/code/bev_render.py`** — 화면 합성 전담(1600x900). `live_demo.py`는 상태만
  넘기고 그리기에 관여하지 않는다. 하드웨어 없이 `--selftest`로 시나리오 8종 PNG를 뽑아 레이아웃을
  검증할 수 있다 (실제로 이걸로 확인하고 올림)
- BEV는 마커가 아니라 **LiDAR 실제 리턴 포인트**로 그린다: 지면 제거 통과분 = 흐린 회색 점,
  매칭 확정 = 해당 방향·거리대 점을 클래스 색으로 재채색 + 후광 + 거리 라벨, 미확정 = 부채꼴
  (폭 `2×sigma`), 6m 이내 = 사각 구역 점등
- **동시 감지 표시 방식 변경** — 우선순위 낮은 대상을 우측 상단 아이콘으로 대신하던 8/26 방식은
  폐기. 이제 BEV가 모든 대상을 좌표로 직접 표시한다("지도는 전부, 알림은 하나"를 문자 그대로)
- **Detection 박스가 실제 bbox 좌표로 그려진다** — 이전 코드는 YOLO가 준 좌표를 버리고 화면
  1/3~2/3에 고정 사각형을 그렸다. 영상에 "Ambulance 92%"가 구급차 아닌 자리에 붙어 남는 문제라
  이번에 같이 고침
- **폴백 유지** — LiDAR가 죽거나 `LIDAR_AVAILABLE=False`여도 BEV는 계속 그려진다(링·자차·부채꼴은
  오디오 방향만으로 성립). 거리·클러스터만 빠지고 좌하단에 "LiDAR 미연결 — 방향만 표시"가 뜬다.
  9/3 go/no-go의 폴백 경로는 그대로 살아 있음
- 성능: 감지 2건 표시 시 6.7ms/프레임, 평상시 4.8ms (카메라 상한 30Hz에 여유). 한글 텍스트는
  내용이 바뀔 때만 다시 그리도록 캐시 — 안 하면 텍스트 합성만으로 14ms가 들어 프레임을 떨어뜨린다
- ⚠️ **이 화면 구현은 렌더링만 검증됐다.** 실제 LiDAR 포인트가 BEV에 제대로 뜨는지, 각도 규약이
  차량 기준으로 맞는지는 실물 연동 때 확인해야 한다 (아래 "미검증" 참고)

### 클래스별 알림 규칙 재정의 (2026-09-02, 팀 논의)

세 클래스가 "라이다로 거리가 확정되면 경고, 아니면 주의"라는 한 규칙을 공유하던 것을, 소리마다
운전자가 알아야 할 것이 다르다는 판단으로 갈랐다. 구현·검증: `08_Video_Demo/code/alert_policy.py`
(`--selftest`로 규칙 22개 검증).

| 소리 | 규칙 |
|---|---|
| **경적** | 거리 안 잼. 여러 방향 동시 발생 시 **가장 큰 소리**가 배너를 차지하고 4초 유지(짧은 소리라 3초로는 운전자가 보기 전에 사라짐). 유지 중이라도 더 큰 경적이 오면 즉시 교체, 1.5초가 지난 뒤에는 작은 경적도 새 사건으로 인정. **같은 방향(±40°)에서 12초 안에 2회 이상 → 주의에서 경고로 승격** (한 번은 지나가는 신호일 수 있지만 두 번째는 나를 향한 것) |
| **사이렌** | **항상 경고.** 위치 확정 여부와 무관 — 긴급차량은 운전자가 위치를 알고 있어야 한다는 판단(양보 의무). 확정되면 거리가, 미확정이면 방향만 붙는다 |
| **오토바이** | 라이다 거리 → 카메라 Detection → 배기음 순으로 근거를 찾는다. 사각지대/15m 이내 = 경고, 15~25m = 주의, 거리는 없지만 **Detection 성공 = 경고**, 둘 다 실패해도 **배기음이 크고(≥ -26dBFS) 또렷하면(SVM 마진 ≥ 0.8) = 경고("사각지대 추정")**, 그 외 = 주의("방향 미확정") |

- 배너에 **판단 근거를 같이 표시**한다 — "경고 → 좌측 · 사각지대 추정", "경고 → 우측 · 반복 2회"
- **오토바이 소리만으로 경고를 낼 수 있게 된 것이 핵심.** 벽 뒤·근접 사각이 가장 위험한데 하필
  라이다·카메라가 둘 다 못 보는 구간이라, 소리만으로 경고가 나가야 "사각지대 경고" 차별점이 성립한다
- **젯슨 패킷에 `rms_db`(dBFS 음량) 추가** — 위 두 규칙(가장 큰 경적, 배기음 크기)이 음량을 요구하는데
  기존 패킷엔 음량 필드가 없었다. `jetson_audio_sender.py`가 분석 구간 ch0의 RMS를 계산해 보낸다
- ⚠️ **음량 임계값은 전부 미보정 추정치.** `rms_db`는 절대 음압(dB SPL)이 아니라 마이크 입력 기준
  상대값이라 차량·마운트·주행 소음에 따라 통째로 밀린다. 장착 후 실제 주행에서 오토바이 배기음과
  배경 소음의 dB를 찍어보고 `alert_policy.MOTO_LOUD_DB`부터 다시 맞출 것
- ⚠️ **"라이다 없으면 전부 주의로 캡"하던 폴백은 더 이상 쓰지 않는다.** 그 캡은 모든 판정이 거리에
  매여 있던 시절의 안전장치였는데, 이제 사이렌은 거리와 무관하게 경고이고 오토바이는 Detection·
  배기음 경로가 따로 있다. 라이다가 없으면 **거리 숫자와 점 클러스터만 빠지고 위험 판정은 유지**된다

### ⚠️ 각도 규약 주의 (구현 중 발견)

시스템 `theta`는 **전방 0°, 반시계 +**(`select_camera(90)=="left"`)인데, 목업 SVG는 시계 +
(0=전, 90=우)로 그려져 있었다. `bev_render._screen_angle()`에서 한 번만 부호를 뒤집어 맞춘다 —
빠뜨리면 BEV 전체가 좌우 반전돼 왼쪽 사이렌이 오른쪽에 뜬다. 목업 코드를 그대로 옮길 때 주의.

## 시스템 아키텍처 — Jetson/노트북 분리 (신규 확정)

기존에는 Jetson 한 대가 오디오+영상+거리+화면을 전부 처리하는 구조로 설계돼 있었으나, **Jetson은 오디오만 전담**하고 나머지는 노트북이 처리하는 구조로 전환됨.

```
[Jetson] 오디오 전담
  - 4채널 수음 (마이크 어레이 입력)
  - 소리 종류 분류 (사이렌·경적·배기음)
  - 소리 방향 추정 (오차 ±10~20°)
  → 아래 JSON 한 줄만 노트북으로 전송 (영상·점군은 오가지 않음). 실측 주기 1.22초

[노트북] 영상·거리·화면
  - 소리 방향에 해당하는 카메라 영상 확인
  - 경광등 점멸 검출 (평상시 경로, 학습 없이 ~0.5초)
  - 야간/악천후로 경광등이 안 보이면 소리 방향 변화 + 차량 움직임 대조 (대체 경로)
  - LiDAR로 후보 차량들의 거리 측정 → 소리 방향과 맞는 차량 특정
  - BEV 지도 + 테두리 알림으로 화면 표시
```

### Jetson→노트북 인터페이스 (JSON, 실측 약 0.8회/초)

```json
{
  "t": 1751250042.318,
  "class": "siren",
  "conf": 0.91,
  "theta": 194.0,
  "sigma": 12.0,
  "rms_db": -22.4
}
```

| 필드 | 설명 |
|---|---|
| `t` | 분석 구간의 **중심 시각** (구간 시작 시각 아님) |
| `class` | `siren` / `horn` / `motorcycle` / `none` |
| `conf` | 0.0~1.0 |
| `theta` | 차량 좌표계 방위각 (전방 0°, 반시계 +) |
| `sigma` | 방향 오차 표준편차(도) — BEV 부채꼴 폭(`2×sigma`)에 사용 |
| `rms_db` | (2026-09-02 추가) 분석 구간 ch0의 RMS 음량(dBFS) — "가장 큰 경적 선택", "배기음 크면 사각지대 추정 경고" 두 규칙이 사용 |

**시각 동기화 원칙**: LiDAR는 한 바퀴 스캔에 100ms가 걸려 같은 프레임 안에서도 관측 방향에 따라 최대 100ms 시각차가 생김(50km/h면 100ms에 약 1.4m 이동) → **프레임 시각이 아니라 점(대상)별 시각을 사용**해 오디오와 매칭. 자세한 내용은 `06_Display_Integration/ui_state_spec.md` §7 참고.

## 젯슨 GPU(CUDA) — 미인식 문제 해결됨

> ⚠️ 이 절은 `main` 브랜치에만 있던 내용이다(2026-08-17 작성). 2026-09-02 병합 시 되살렸다.

**(2026-08-17 추가) GPU 미인식 문제 원인 확인 및 해결됨**
- 원인: `pip install torch`로 설치된 게 일반 PyPI 빌드(`torch 2.12.1+cu130`)였음 — 이 젯슨(JetPack 6.x, L4T R36.4.7, CUDA 12.6)의 Tegra 내장 GPU용으로 빌드된 게 아니라 x86/dGPU용 CUDA 13.0 스택을 기대하는 빌드라 `torch.cuda.is_available()`이 계속 False였음
- 해결: NVIDIA Jetson AI Lab이 JetPack별로 따로 빌드해 배포하는 pip 인덱스(`https://pypi.jetson-ai-lab.io/jp6/cu126`)에서 설치. **주의**: `--extra-index-url`로 일반 PyPI를 같이 열어두면 pip이 버전 높은 일반 빌드를 다시 골라버려 문제가 재발함 — 반드시 `--index-url`만 쓰고 버전을 명시할 것
  - 처음 시도한 `torch==2.11.0`은 `libcudss.so.0` 공유 라이브러리 누락으로 import 자체가 실패함(이 인덱스엔 대응하는 cuDSS 패키지가 없음, aarch64용 `nvidia-cudss-cu12`도 PyPI에 없음) → 한 버전 낮은 `torch==2.8.0` + `torchvision==0.23.0` 조합으로 정상 동작 확인
  - 확인됨: `torch.cuda.get_device_name(0)` → `"Orin"`, capability `(8, 7)`
- **실측 벤치마크** (실제 체크포인트, 유휴 상태 기준, 1.0s 오디오 윈도우): CPU 평균 278ms → CUDA 평균 78ms (약 3.6배)
  - ⚠️ 이 78ms는 카메라·LiDAR·ROS2 없이 이 스크립트 하나만 유휴 상태에서 돌린 수치라, 기존에 관측된 "실외 15초" 현상을 이 벤치마크만으로 완전히 설명한다고 단정할 수 없음 — 다른 노드들과 동시 구동 시, 그리고 실제 실외(발열/직사광선에 의한 Orin Nano 스로틀링 가능성)에서 재측정 필요
  - `pip3 check` 결과 `torchvision`/`ultralytics` 등 다른 패키지와 충돌 없음 확인 (orphan 패키지 경고 2건은 무관)
- 다음 단계: 위 벤치마크만으로도 실시간 목표(초당 4회, 250ms)에 여유 있게 들어오므로, TensorRT 변환은 급하지 않을 수 있음 — 우선 젯슨에서 카메라·LiDAR·ROS2까지 다 켠 상태로 `realtime_classify.py --device cuda` 재측정해서 실사용 환경 지연부터 확인할 것

**(2026-09-02 후속) 원인은 CUDA 미설치가 아니라 코드였다.**

이날 실측한 젯슨 추론이 1.0초 창에 약 0.2초로 위 CPU 벤치마크(278ms)에 가까워
"CUDA가 꺼져 있나" 의심했으나, 확인해보니 젯슨은 **`torch.cuda.is_available() == True`,
torch 2.8.0**(위 Jetson AI Lab 빌드)로 정상이었다.

진짜 원인은 `03_Audio_Classification/code/realtime_classify.py`의 `load_panns_model()`이
**모델을 GPU로 옮기지 않는 것**이었다:

```python
ckpt = torch.load(ckpt_path, map_location="cpu", ...)
model.load_state_dict(ckpt["model"]); model.eval()
return model          # ← .to(device) 가 없어 CPU에 남는다
```

`torch.cuda.is_available()`이 True인 것과 모델이 GPU에 올라가는 것은 별개다. 8/17에
CUDA 환경을 고쳐놓고도 **추론은 계속 CPU에서 돌고 있었다**(3.6배 손해).

**해결(2026-09-02)**: `load_panns_model(ckpt_path, device="auto")`로 장치 인자를 받아
`model.to(dev)`하고, `classify()`도 입력 텐서를 같은 장치로 보낸 뒤 임베딩만 CPU로
내려받도록 수정. CUDA일 때는 기동 시 워밍업 1회(첫 호출이 커널 컴파일로 유독 느린 것을
흡수). 젯슨 송신기에 `--device auto|cpu|cuda` 옵션 추가(기본 auto).

**실측 결과 (2026-09-02, 수정 직후)**

| | 주기 | 구성 |
|---|---|---|
| CPU (수정 전) | 1.220s | 수음 1.024s + 추론·처리 0.196s |
| **CUDA (수정 후)** | **1.024s** | 수음 1.024s + 추론·처리 **≈0** |

**주기가 수음 시간과 같아졌다**(실측 1.007~1.029s). 추론이 수음하는 동안 끝나서 이제
병목은 "1초를 듣는 시간"뿐이다. 감지 빈도 0.82회/초 → 0.98회/초 (19% 개선).

의미는 속도보다 **젯슨 CPU가 놀게 된 것**에 있다. 이전엔 매 주기 200ms씩 CPU를 점유했는데
그게 GPU로 넘어갔다 — 실외 발열로 Orin Nano가 스로틀링될 때 여유가 생긴다(8/17에 기록된
"실외 15초 지연" 현상의 재발 위험 감소).

여기서 더 줄이려면 수음 구조를 바꿔야 한다. 지금은 "1초 듣고 → 판단 → 다시 1초 듣고"인데,
별도 스레드로 계속 들으면서 0.25초마다 최근 1초를 판단하는 **슬라이딩 윈도우**로 바꾸면
인터페이스 스펙(초당 4회)에 도달한다. 다만 9/8 촬영에는 불필요하다 — 1초 주기로 충분하고,
지금 손대면 검증 안 된 코드로 촬영하게 된다.

기동 시 `[*] PANNs 장치: cuda (Orin)`이 찍히는지로 확인할 수 있다.

| 상태 | 의미 | 상단 알림 | 지도 | 테두리 빛 |

| `주의` | 접근 중/위치 미확정 | 노란 막대 | 부채꼴 또는 노란 마커 | 약하게(45%) |
| `경고` | 근접/사각지대/차량 확정 | 빨간 막대 | 빨간 마커 또는 구역 점등 | 강하게(90%) |

- **원칙**: 지도는 감지된 모든 대상을 표시, 상단 알림·테두리 빛은 최우선 대상 하나만 반영
- **위치 미확정 시에는 특정 차량에 마커를 찍지 않고 부채꼴(방향+오차범위)로만 표시** — "잘못된 지목은 알려주지 않는 것보다 위험하다"는 원칙
- 상태 진입은 즉시, 하향/해제는 지연(3초 유지 후 0.5초에 걸쳐 해제) — 소리가 순간 끊겨도 알림이 깜빡이지 않도록

## 소리별 대응 방식 (오토바이 경고가 핵심 차별점)

| 소리 | 대응 |
|---|---|
| 사이렌(긴급차량) | 경광등 점멸로 찾음 → LiDAR로 거리 측정 → 지도에 차량 위치 표시. **(2026-09-02) 위치가 확정되지 않아도 항상 "경고"** |
| 배기음(오토바이) | 골목·근접 주행 모두 대응, 벽 뒤는 소리로 미리 감지, 가까이 붙으면 지도 표시, 위험도 단계 구분. **(2026-09-02) 라이다·카메라가 둘 다 못 봐도 배기음이 크고 또렷하면 "사각지대 추정" 경고** |
| 경적(일반 차량) | 즉각 방향 표시 + 해당 방향 카메라, **거리는 추정하지 않음**. **(2026-09-02) 동시 발생 시 가장 큰 것을 선택, 같은 방향 반복 시 경고로 승격** |

### 오토바이 경고 5단계

| 상황 | 단계 | 화면 표시 |
|---|---|---|
| 주변에 있으나 멀어짐 | 표시 | 회색 점, 알림 없음 |
| 15~25m 접근 | 주의 | 노란 마커 |
| 15m 이내 근접 | 경고 | 빨간 마커 + 테두리 빛 (깜빡임 주기 = 거리에 반비례, 0.3~1.2초) |
| 사각지대(반경 6m 이내, LiDAR 사각) 진입 | 경고 | 점 대신 **사각 구역 자체를 점등** (0.3초 고정 깜빡임) — 없는 정확도를 있는 것처럼 보이지 않기 위함 |
| 벽에 가린 골목 | 주의 | 부채꼴 + "시야 밖" 표시, 방향은 오토바이가 아니라 **골목 입구**를 가리킴 |

> 도심에서 매번 경고하면 운전자가 곧 알림을 무시하게 됨 → 상황별 단계 구분이 핵심. 기존 양산 차량 경고 기능(옆 차선 일부만 감지)과 달리 **360° 전방향 + 벽 뒤 골목 감지**가 차별점.

## 진행 계획 (M1~M5, 중간보고 기준)

| 단계 | 내용 | 상태 |
|---|---|---|
| M1 | 소리 인식 개선 — 방풍 커버 장착 후 주행 정확도 재측정 | 준비 |
| M2 | 방향 추정 — 사이렌 전용 방향 추정 적용 | 준비 |
| M3 | 카메라 전환 — 소리 방향 카메라 화면 자동 표시 | **시연 가능** |
| M4 | 경광등 검출 — 점멸 인식 + LiDAR 거리 연결 | 확장 |
| M5 | 오토바이 경고 — 배기음 데이터 수집, 골목·근접 경고 | 확장 |

- **3단계(M3) 이후로는 언제든 시연 가능한 상태 유지**가 목표
- 측정 항목: 인식 정확도(속도별·소리 종류별), 방향 오차(실제 각도 대비), 지목 정확도(정답 차량 선택률), 오경보 횟수(일반 주행 10분당)
- 시험 방법: 다른 차량 지붕에 스피커를 얹고 함께 주행 → 그 차량이 정답. 긴급차량은 별도 학습 데이터 불필요, **오토바이 배기음만 직접 녹음** 필요 (주행 소음 섞어 학습해야 실도로 성능 유지)
